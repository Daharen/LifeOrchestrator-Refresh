## 0. Normative conventions

### 0.1 Security objective

The security invariant is not that a model resists prompt injection. The model, retrieved evidence, navigation records, working memory, skill cards, and tool text may all be fully attacker-influenced. The invariant is:

> Untrusted content may influence an action proposal, but it cannot construct or modify authority, widen scope, define actual effects, create a permit, satisfy completion, or cause an executor-visible side effect without a current one-shot permit bound to the exact canonical action.

### 0.2 Trust classes

Every field and runtime value has exactly one origin class.

| Class | Meaning | May authorize? | Normal derivation rule |
|---|---|---:|---|
| `Authority<T>` | Value loaded from the coordinator/user authority store, trusted manifest registry, grant store, approval store, side-effect-policy store, completion-contract store, or permit issuer | Yes, only where this contract explicitly says so | May derive only from other `Authority` values or an explicit elevated human/administrator operation outside the ordinary model path |
| `Request<T>` | User/coordinator request expressing desired work or requested scope | No | Remains a request; intersection with authority may narrow it but never turns the request itself into a grant |
| `Untrusted<T>` | Model output, retrieved evidence, navigation content, working-memory content, skill/procedure prose, imported records, caller-supplied proposal fields, and tool text | No | Copy, summarize, cluster, transform, decode, or promote through an ordinary path preserves `Untrusted` |
| `TrustedStatus<T>` | Narrow structured observation emitted by an allowlisted trusted runtime component, executor, validator, trusted clock, or health probe | No general authority; may satisfy only the exact status predicate that names its source and type | Cannot define policy, grants, manifests, approval requirements, or completion rules |

There is no implicit conversion from `Request`, `Untrusted`, or `TrustedStatus` to `Authority`. A value that merely has an authority-shaped field name remains non-authoritative.

### 0.3 Primitive types

- `id`: ASCII string matching `[A-Za-z0-9._:-]{1,256}`. Where a field is generated by trusted code, its producer SHOULD use the relevant stable prefix (`prop_`, `permit_`, `grant_`, etc.), but prefixes are not authorization evidence.
- `namespaced_id`: ASCII string matching `[a-z][a-z0-9._:-]{0,127}`.
- `sha256`: exactly 64 lowercase hexadecimal characters.
- `uint63`: integer in `[0, 9223372036854775807]`.
- `risk_class`: integer enum `0 | 1 | 2 | 3 | 4`, where larger is more restrictive. The names are `0=none`, `1=low`, `2=moderate`, `3=high`, `4=critical`.
- `namespace_id`: opaque string interpreted only by the shipped canonical `ns_permitted` predicate. The action layer MUST NOT add wildcard, prefix, parent, shared, or case-fold semantics.
- Optional fields are absent when unused. `null` is forbidden unless a field explicitly says otherwise.
- JSON numbers are integers only. Floating-point values, `NaN`, and infinities are forbidden.

### 0.4 Strict parsing and canonical serialization

All four contracts use one strict parser and one canonical serializer.

1. Input MUST be valid UTF-8; byte-order marks, invalid sequences, and lone surrogates are rejected.
2. Duplicate object keys are rejected before schema validation.
3. Contract byte limits are exact: proposal 1,048,576 bytes; manifest 4,194,304 bytes; permit 4,194,304 bytes; completion contract 2,097,152 bytes. Maximum JSON depth is 16, maximum members per object is 1,024, and maximum items in any array is 4,096 unless a field sets a smaller bound.
4. Unknown fields are rejected in every closed object.
5. No type coercion is permitted: strings do not become integers or booleans; singleton values do not become arrays.
6. Object keys are serialized in ascending Unicode code-point order.
7. Arrays preserve order unless the field is explicitly a set; set-valued arrays are deduplicated and sorted by their canonical element bytes.
8. Canonical JSON uses UTF-8, no insignificant whitespace, lowercase JSON literals, and one trailing LF.
9. Unicode content is preserved losslessly. A field is NFC-normalized only when its trusted manifest schema explicitly marks that field `normalize_nfc=true`; the original request value remains available for audit. Evidence is never rewritten or sanitized.
10. Hashes are SHA-256 over canonical bytes. A self-hash field is omitted while computing the hash.
11. Parser, serializer, canonicalizer, resolver, effect-classifier, grant-matcher, and executor MUST use the same versioned library or prove byte-equivalence with shared fixtures.

### 0.5 Caller-visible denial

Every authorization denial visible to an ordinary caller is the same constant object:

```json
{"schema":"lifeorch.authorization_result/0.1","status":"denied","code":"AUTHZ_DENIED"}
```

No proposal field, record id, path, namespace, target count, grant id, manifest detail, failure stage, or timing-derived diagnostic is returned to the ordinary caller. Detailed reason codes and identifiers go only to a bounded privileged local security log. A denial produces no permit and no executor state change.

### 0.6 Canonical action

The authorizer constructs, but never accepts from the proposal, this internal closed object:

```text
CanonicalAction/0.1 {
  schema: const "lifeorch.canonical_action/0.1",
  tool_id: namespaced_id,
  tool_manifest_version: uint63,
  tool_manifest_digest: sha256,
  operation: namespaced_id,
  canonical_arguments: object,
  resolved_target_set: ResolvedTarget[],
  derived_effect_set: EffectAtom[],
  action_namespace: namespace_id,
  risk_class: risk_class,
  sandbox_class: enum,
  limits: LimitAtom[],
  idempotency_key: id
}
```

`canonical_action_digest = SHA256(canonical_bytes(CanonicalAction))`.

The digest therefore binds the exact manifest, operation, canonical arguments, resolved targets, derived effects, namespace, risk, sandbox, limits, and idempotency key. It contains no wall-clock value and no attacker-controlled prose.

`ResolvedTarget` is a closed trusted-derived object:

```text
{
  target_kind: namespaced_id,
  canonical_target_id: id,
  namespace: namespace_id,
  resolution_kind: "existing" | "future" | "logical",
  resolution_proof_digest: sha256
}
```

The array is a sorted unique set ordered by canonical bytes. `canonical_target_id` is the executor identity, not merely the caller's spelling. Alias, recipient, path, redirect, reparse-point, symlink, junction, wrapper, environment-variable, wildcard, and case behavior is resolved by the trusted manifest operation profile before this object exists.

`EffectAtom` is a closed trusted-derived object:

```text
{
  effect_class: namespaced_id,
  target_index: uint63,
  quantity: uint63,
  unit: namespaced_id,
  effect_risk_class: risk_class,
  externality: "local" | "private_external" | "public_external",
  reversibility: "reversible" | "compensatable" | "irreversible"
}
```

`target_index` references `resolved_target_set`. The set is sorted unique by canonical bytes. Unknown effect classes or units are denied. A zero quantity is allowed only where the manifest operation profile explicitly allows it.

`LimitAtom` is:

```text
{ limit_id: namespaced_id, max_value: uint63 }
```

The set is sorted unique by `limit_id`. Unknown limit ids are denied by the executor.

## 1. `lifeorch.action_proposal/0.1`

### 1.1 Purpose and trust

An action proposal is a non-executable, attacker-controlled request emitted by a model-facing adapter. It is never a tool call, grant, approval, manifest, permit, completion result, or trusted status.

### 1.2 Exact field list

| Field | Type | Req. | Trust class | Authorization use |
|---|---|:---:|---|---|
| `schema` | const `"lifeorch.action_proposal/0.1"` | yes | `Untrusted` | Schema dispatch only |
| `proposal_id` | `id` | yes | `Untrusted` | Audit/dedup only; never permission |
| `task_id` | `id` | yes | `Untrusted` | Lookup key that must match trusted packet/task state |
| `packet_id` | `id` | yes | `Untrusted` | Lookup key that must resolve to an authentic packet |
| `tool_id` | `namespaced_id` | yes | `Untrusted` | Requested tool only |
| `operation` | `namespaced_id` | yes | `Untrusted` | Requested operation only |
| `arguments` | JSON object | yes | `Untrusted` | Validated, canonicalized, and resolved under the trusted manifest |
| `evidence_refs` | sorted unique array of `id`, max 256 | yes | `Untrusted` | Audit/explanation only; cannot grant or satisfy completion |
| `claimed_effects` | array of JSON objects, max 256 | yes | `Untrusted` | Advisory only; excluded from actual-effect derivation and grant matching |
| `model_provenance` | `ModelProvenance` | yes | `TrustedStatus` | Audit and packet/run binding only; never permission |

`ModelProvenance` is attached by the trusted model adapter after parsing the model body. A model-supplied field with this name is rejected as a duplicate/forgery.

```text
ModelProvenance {
  model_run_id: id,
  adapter_id: namespaced_id,
  adapter_version: uint63,
  consumer_profile_fingerprint: sha256,
  prompt_packet_id: id,
  raw_output_hash: sha256
}
```

### 1.3 Invariants

1. The object is accepted only by the action-proposal parser, never by an executor.
2. It contains no field capable of selecting a grant, setting approval state, setting risk, defining a manifest, defining a completion predicate, choosing an issuer, or supplying a permit.
3. `task_id`, `packet_id`, `tool_id`, `operation`, and `arguments` are claims to be checked, not trusted references.
4. `prompt_packet_id` MUST equal `packet_id`; mismatch denies.
5. `claimed_effects` MUST have no effect on authorization outcome except that gross size/schema limits may cause denial. Replacing it with any other bounded value cannot turn a denial into a permit or change the permit's action digest.
6. `evidence_refs` cannot establish evidence sufficiency; the trusted packet's coverage and disposition do that.
7. A proposal may refer only to one operation. Batch actions require a manifest-defined batch operation whose complete target/effect set is derived and authorized as one canonical action.
8. The proposal remains `Untrusted` through parsing, normalization, retries, summaries, storage, and replay.
9. A proposal has no inherent freshness. Freshness is determined from the trusted packet, grant, manifest, approval, health, and status stores at authorization time.
10. Unknown or duplicate fields deny; they are not ignored.

It is loaded only from an allowlisted installed-code registry. Retrieved skill cards, procedures, README files, tool descriptions, model output, and tool text may describe a tool but can never define or override this object.

Every field in this contract is `Authority`.

### 2.4 `ClosedArgSchema`

The manifest uses a deliberately small deterministic schema rather than unrestricted JSON Schema.

```text
ClosedArgSchema {
  type: const "object",
  additional_properties: const false,
  fields: sorted unique FieldSchema[]
}

FieldSchema {
  name: namespaced_id,
  type: "string" | "integer" | "boolean" | "object" |
        "string_array" | "integer_array" | "object_array",
  required: boolean,
  normalize_nfc: boolean,
  set_semantics: boolean,
  min_value?: uint63,
  max_value?: uint63,
  min_items?: uint63,
  max_items?: uint63,
  min_utf8_bytes?: uint63,
  max_utf8_bytes?: uint63,
  enum_values?: sorted unique JSON scalar array,
  semantic_type: "opaque" | "path" | "uri" | "recipient" | "object_id" |
                 "duration_ms" | "quantity" | "content",
  validator?: CodeProfileRef,
  object_schema?: ClosedArgSchema
}
```

Rules:

- Constraints inapplicable to the selected type are absent.
- `object_schema` is present only for `object` and `object_array`.
- Maximum nesting depth is 16; maximum total fields after expansion is 1024.
- Arrays with `set_semantics=true` are canonicalized to sorted unique elements; otherwise order is preserved and semantically significant.
- `content` may contain arbitrary lossless text but remains untrusted data.
- `path`, `uri`, `recipient`, and `object_id` are not authorized by string validation; they must be resolved by `target_resolver`.

### 2.5 Manifest invariants

1. The manifest registry is allowlisted and writable only through an elevated non-model administration path.
2. A manifest is immutable at a given `(tool_id, manifest_version)`; changing any field requires a new version and digest.
3. The installed artifact digest must match before authorization and again before execution.
4. Each operation id is unique. Unknown, disabled, or case-variant operations deny.
5. The argument schema is closed; no unknown field is passed to canonicalization or execution.
6. Canonicalizer, resolver, and effect classifier are pure over their declared inputs and pinned local snapshots. Any I/O needed for resolution occurs through a bounded trusted resolver interface and returns a deterministic result at the pinned resolution snapshot.
7. The resolver returns only declared target kinds and no more than `max_target_count` targets.
8. The classifier returns only declared effect classes, references valid target indexes, and returns no more than `max_effect_count` effects.
9. Effective risk is `max(base_risk_class, every effect_risk_class, applicable side-effect-policy escalation)`.
10. A card, procedure, model, evidence item, filename, log, diagnostic, or tool output cannot set `enabled`, risk, health, approval, effects, required scopes, rollback, idempotency, or sandbox.
11. A meta-tool, shell wrapper, script runner, redirector, or batch operation must classify the effects of the wrapped action, not merely the wrapper process.
12. The manifest MUST NOT declare a generic “arbitrary command” or unconstrained target/effect class for an action-capable release. Such an operation remains disabled or proposal-only.

## 3. `lifeorch.action_permit/0.1`

### 3.1 Purpose and trust

A permit is an immutable `Authority` object issued only by the deterministic reference monitor after all checks pass. It is one-shot, short-lived, bound to one exact canonical action, and never rendered into an ordinary model context. A model cannot construct one by emitting permit-shaped JSON.

### 3.2 Exact field list

Every field is required and `Authority` unless marked optional.

| Field | Type | Req. | Meaning |
|---|---|:---:|---|
| `schema` | const `"lifeorch.action_permit/0.1"` | yes | Contract id |
| `permit_id` | `id` | yes | Unique issuer-generated id |
| `issuer` | `namespaced_id` | yes | Trusted reference-monitor identity |
| `issuer_version` | `uint63` | yes | Reference-monitor version |
| `issued_at_unix_ms` | `uint63` | yes | Trusted-clock issue time |
| `expiry_unix_ms` | `uint63` | yes | Exclusive expiry; must be greater than issue time |
| `task_id` | `id` | yes | Trusted resolved task binding |
| `packet_id` | `id` | yes | Exact authentic packet binding |
| `canonical_action_digest` | `sha256` | yes | Hash defined in §0.6 |
| `tool_id` | `namespaced_id` | yes | Exact manifest tool |
| `tool_manifest_version` | `uint63` | yes | Exact manifest version |
| `tool_manifest_digest` | `sha256` | yes | Exact manifest digest |
| `operation` | `namespaced_id` | yes | Exact operation |
| `canonical_arguments` | JSON object | yes | Exact trusted-canonicalized arguments used by the executor |
| `risk_class` | `risk_class` | yes | Exact effective action risk |
| `resolved_target_set` | sorted unique `ResolvedTarget[]` | yes | Exact authorized targets |
| `authorized_effect_set` | sorted unique `EffectAtom[]` | yes | Exact authorized effects |
| `effective_namespace` | `namespace_id` | yes | One action namespace in v0.1 |
| `grant_snapshot_ref` | `id` | yes | Exact trusted grant snapshot |
| `matched_grant_ids` | nonempty sorted unique array of `id` | yes | Grants whose conjunction authorizes the action |
| `side_effect_policy_ref` | `id` | yes | Exact trusted policy snapshot |
| `approval_ref` | `id` | conditional | Required when approval is required; absent otherwise |
| `limits` | sorted unique `LimitAtom[]` | yes | Effective minima across manifest, grants, policy, approval |
| `sandbox_class` | sandbox enum | yes | Exact execution sandbox |
| `nonce` | 32 lowercase hex chars | yes | Issuer-unique 128-bit token; uniqueness, not secrecy, is the invariant |
| `idempotency_key` | `id` | yes | Exact action idempotency identity |
| `permit_store_epoch` | `uint63` | yes | Trusted permit-store generation |
| `permit_digest` | `sha256` | yes | Hash of canonical permit with this field omitted |

The permit store, not caller-supplied JSON, is authoritative. The executor receives a permit reference over a privileged in-process/IPC channel and resolves the immutable permit and its canonical action from the trusted permit store. If serialized permit bytes are transported, the executor still requires an exact store match by `permit_id` and `permit_digest`.

### 3.3 One-shot state machine

Permit mutable state is stored separately and atomically:

```text
issued -> claimed -> consumed
issued -> revoked
issued -> expired
claimed -> rejected_no_effect
claimed -> consumed
```

- `claimed` is entered by compare-and-swap before any executor preflight that could race another executor.
- Only `issued` may be claimed.
- Every terminal state is permanent.
- A preflight failure after claim produces `rejected_no_effect`; the permit cannot be retried.
- The first side-effecting instruction transitions the permit to `consumed` atomically with recording `effect_started=true`.
- A crash after `effect_started=true` is recovered through idempotency/state-diff logic; it never makes the permit reusable.

### 3.4 Permit invariants

1. A permit exists only in the trusted store; permit-shaped model/evidence/tool text is ignored and rejected by the executor.
2. `canonical_arguments`, `resolved_target_set`, `authorized_effect_set`, namespace, risk, sandbox, limits, and idempotency key exactly match the canonical action digest.
3. `expiry_unix_ms - issued_at_unix_ms` is bounded by the applicable policy and never exceeds the smallest grant/approval/manifest validity remainder.
4. v0.1 authorizes exactly one namespace. If resolved targets or effects span more than one namespace, authorization denies; the caller must split the work into separately authorized actions.
5. One permit authorizes one canonical action invocation. It cannot be reused for a retry, rollback, follow-up, or second batch.
6. Rollback is a new action proposal and new permit, unless an executor-local atomic rollback is part of the manifest-defined operation transaction and already included in the canonical effects.
7. The permit is not inserted into `control_plane`, `task_input`, `working_memory`, `evidence`, navigation diagnostics, ordinary logs, or model prompts.
8. Revocation of the grant, approval, permit, tool, or policy before `claimed` causes denial. The executor rechecks current state immediately before claim.
9. Manifest or installed-artifact drift causes denial even if the operation name and arguments are unchanged.
10. Re-resolved target identity must match the permit before effect. A changed alias, symlink, junction, redirect, recipient mapping, or object identity denies.
11. Executor-observed effects must be a subset of `authorized_effect_set` and within every `LimitAtom`. An undeclared or over-limit effect aborts before that effect where technically possible and records a security violation.
12. Every denied proposal and every rejected permit produces no state diff.

## 4. `lifeorch.completion_contract/0.1`

### 4.1 Purpose and trust

The completion contract defines deterministic trusted predicates for deciding whether a task/action is complete. It is `Authority`, loaded only from the control-plane authority store. Model output, evidence prose, navigation text, working memory, skill cards, untrusted tool text, and filenames can never define, modify, waive, or satisfy it.

### 4.2 Exact field list

Every field is `Authority`.

| Field | Type | Req. | Meaning |
|---|---|:---:|---|
| `schema` | const `"lifeorch.completion_contract/0.1"` | yes | Contract id |
| `completion_contract_id` | `id` | yes | Stable logical contract id |
| `contract_version` | `uint63` | yes | Immutable version |
| `task_id` | `id` | yes | Exact task binding |
| `effective_namespace` | `namespace_id` | yes | Namespace in which status subjects may resolve |
| `grant_snapshot_ref` | `id` | yes | Authority snapshot under which the contract was established |
| `root` | `CompletionExpr` | yes | Closed three-valued predicate tree |
| `trusted_status_sources` | nonempty sorted unique `StatusSourceRef[]` | yes | Allowlisted status producers |
| `evaluation_policy` | const object described below | yes | Fail-closed evaluation |
| `contract_digest` | `sha256` | yes | Hash with this field omitted |

`evaluation_policy` is exactly:

```json
{"missing":"indeterminate","malformed":"indeterminate","stale":"indeterminate","indeterminate_is_complete":false}
```

`StatusSourceRef` is:

```text
{
  source_id: namespaced_id,
  source_version: uint63,
  status_schema: namespaced_id,
  code_digest: sha256,
  max_age_ms: uint63
}
```

### 4.3 Predicate expression

`CompletionExpr` is a closed tagged union with maximum depth 16 and maximum 256 leaves:

```text
{ kind: "leaf", predicate: CompletionPredicate }
{ kind: "all", children: nonempty CompletionExpr[] }
{ kind: "any", children: nonempty CompletionExpr[] }
{ kind: "at_least", threshold: uint63, children: nonempty CompletionExpr[] }
```

For `at_least`, `1 <= threshold <= len(children)`.

Three-valued evaluation is exact:

- `all`: `false` if any child is false; `true` if all are true; otherwise `indeterminate`.
- `any`: `true` if any child is true; `false` if all are false; otherwise `indeterminate`.
- `at_least(k)`: `true` if true-count is at least `k`; `false` if true-count plus indeterminate-count is less than `k`; otherwise `indeterminate`.
- A task is complete only when the root is exactly `true`.

### 4.4 Completion leaf types

Every `CompletionPredicate` has these common fields:

```text
{
  predicate_id: id,
  predicate_kind: enum below,
  source_id: namespaced_id,
  source_version: uint63,
  subject_binding: SubjectBinding,
  max_age_ms: uint63,
  expected: kind-specific closed object
}
```

`SubjectBinding` is:

```text
{
  task_id: id,
  canonical_action_digest?: sha256,
  permit_id?: id,
  object_ref?: id
}
```

A status record can satisfy a leaf only if every present binding field matches exactly.

Closed leaf kinds and expected objects:

1. `executor_status`
   ```text
   { allowed_result_codes: nonempty sorted unique namespaced_id[],
     allowed_exit_codes: sorted unique integer[] }
   ```
   The actual source is trusted structured executor status, not stdout/stderr text.

2. `state_diff`
   ```text
   { validator_id: namespaced_id, validator_version: uint63,
     required_result_code: namespaced_id,
     expected_diff_digest?: sha256 }
   ```

3. `artifact_hash`
   ```text
   { object_ref: id, hash_algorithm: const "sha256", expected_hash: sha256 }
   ```

4. `test_suite`
   ```text
   { validator_id: namespaced_id, validator_version: uint63,
     suite_id: namespaced_id, suite_version: uint63,
     minimum_passed: uint63, maximum_failed: uint63 }
   ```

5. `object_state`
   ```text
   { validator_id: namespaced_id, validator_version: uint63,
     object_ref: id, expected_state_digest: sha256 }
   ```

6. `human_approval`
   ```text
   { approval_ref: id, required_state: const "approved" }
   ```

7. `postcondition`
   ```text
   { validator_id: namespaced_id, validator_version: uint63,
     postcondition_id: namespaced_id,
     expected_result_code: namespaced_id }
   ```

No leaf performs arbitrary code supplied in the contract. Validator identifiers resolve only through a trusted local validator registry. No leaf type performs free-text matching, model judgment, semantic similarity, evidence interpretation, or tool-output prose parsing.

### 4.5 Trusted status requirements

A status record is usable only when all are true:

1. It was emitted by an allowlisted `StatusSourceRef` whose version and code digest still match.
2. It uses the exact declared status schema.
3. It is structurally typed and its trusted fields are separated from any attached untrusted text.
4. Its task/action/permit/object bindings match the leaf.
5. It is fresh under both the source and leaf maximum ages.
6. It is in the contract's effective namespace under `ns_permitted`.
7. It has not been superseded, revoked, or invalidated.
8. Its actual object/artifact identity is canonical, not merely caller-named.

Missing, stale, malformed, ambiguous, conflicting, or unverifiable status yields `indeterminate`, never success.

### 4.6 Completion invariants

1. The contract is created or changed only through an elevated authority path; ordinary model output cannot write it.
2. Each version is immutable; change requires a new version/digest and control-plane snapshot.
3. Completion evaluation is independent of evidence prose and model claims such as “done,” “approved,” “tests passed,” or fake JSON.
4. Tool stdout/stderr, response bodies, shell text, and retrieved logs remain `Untrusted`; they may be retained for diagnosis but cannot satisfy a leaf unless a separate trusted validator produces the exact typed status.
5. A status produced for one action, permit, task, object, namespace, or validator version cannot satisfy another.
6. `indeterminate` is incomplete.
7. Completion does not create authorization for another action.
8. A human-approval completion leaf requires the current trusted approval-store record, not quoted or copied approval text.

## 5. Ordered deny-by-default authorization algorithm

The reference monitor is a pure deterministic decision over explicitly supplied trusted snapshots plus a trusted clock and atomic permit store. The build target is local-only on one Windows box, uses deterministic standard-library-only modules, performs no network access, and invokes no model as a security oracle. Any exception, missing value, ambiguity, unsupported type, conflicting state, or indeterminate result is `DENY`. Checks occur in this order. Each numbered check is independently fixture-testable; deleting or bypassing any check is a mandatory killed mutation.

### Inputs

- `proposal_bytes: Untrusted<bytes>`
- trusted packet store and packet-integrity verifier
- trusted current grant snapshot/store
- trusted side-effect-policy store
- trusted tool-manifest registry
- trusted approval store
- trusted tool-health source
- trusted validator registry/status store
- trusted clock
- atomic trusted permit/idempotency store
- privileged security logger

### Checks

**A01 — Channel/type gate.** Accept only bytes delivered to the proposal endpoint. Reject executor calls, permit-shaped objects, raw model tool-call envelopes, and unknown schema ids.

**A02 — Strict parse.** Parse under §0.4. Duplicate keys, invalid UTF-8, floats, excessive depth/size, unknown fields, or coercion deny.

**A03 — Proposal schema.** Validate the exact `lifeorch.action_proposal/0.1` field types and bounds.

**A04 — Trusted provenance attachment.** Verify `model_provenance` was attached by the trusted adapter, its raw-output hash matches the captured model output, and no model-supplied duplicate existed.

**A05 — Packet lookup and task binding.** Resolve `packet_id` from the trusted packet store; verify its content hash/packet id; require trusted packet `task_id == proposal.task_id` and require `model_provenance.prompt_packet_id == proposal.packet_id`. Lookup failure or mismatch denies with the constant result.

**A06 — Non-execution gate.** Require the trusted packet's `non_execution == false`. While the shipped substrate remains `true`, every proposal deterministically denies here. No local flag, proposal argument, evidence item, or tool manifest may bypass this check.

**A07 — Packet freshness.** Require the packet to be the current permitted packet version for the task and require its pinned corpus, hierarchy/tree, classifier, temporal intent, working-state version, and grant snapshot to remain valid under the action policy. Drift, revocation, unavailable snapshots, or ambiguous currentness denies.

**A08 — Packet disposition.** Record the authentic packet disposition and evidence/coverage state. Do not use proposal `evidence_refs` to replace it. The exact requirement is applied at A31 according to manifest `evidence_dependency`.

**A09 — Current authority snapshot.** Load the current trusted control-plane authority referenced by the packet. Verify policy, permission grants, side-effect policy, completion contract, and escalation conditions originate from the authority store and match their digests/versions. Any value reconstructed from evidence, working memory, navigation, skill cards, or model output denies.

**A10 — Grant freshness and revocation.** Verify the grant snapshot is current, unexpired, not revoked, not superseded, and still authorized for the task/request authority. A stale broader snapshot cannot be replayed.

**A11 — Effective namespace.** Compute authorized namespaces exclusively through the shipped rule: `intersection(Request task_input.namespace, Authority permission_grants)`, using the one imported canonical `ns_permitted` predicate. Never use proposal arguments or raw task namespace as authority. Empty intersection denies. No implicit all/wildcard/prefix/parent/shared scope exists.

**A12 — Trusted manifest lookup.** Resolve `proposal.tool_id` only from the allowlisted manifest registry. Require exact tool id, current enabled registry entry, immutable version/digest, and matching installed artifact digest. Skill/procedure cards and retrieved tool descriptions are ignored for manifest definition.

**A13 — Operation lookup.** Require an exact case-sensitive enabled operation in `manifest.operations`. Unknown, disabled, alias-only, downgraded, or version-substituted operations deny.

**A14 — Tool health.** Load current `TrustedStatus` from the manifest's exact health source. Require source/version/digest, healthy code, and freshness. Text saying “healthy” is irrelevant.

**A15 — Closed argument validation.** Validate `proposal.arguments` against the operation's `ClosedArgSchema`. Reject unknown fields, missing required fields, bad bounds, bad nested schemas, array overflows, and all coercion.

**A16 — Canonicalize arguments.** Invoke the exact trusted canonicalizer profile. Preserve untrusted content as data; canonicalize only fields declared by the schema. Canonicalization error or non-determinism denies.

**A17 — Resolve targets.** Invoke the exact trusted resolver profile. Resolve aliases, paths, reparse points, symlinks, junctions, redirects, wrappers, wildcards, environment expansions, recipients, object ids, and future-create parents according to the operation profile. Unresolved, multiple-meaning, disappearing, forbidden device/alternate-stream, or unsupported targets deny.

**A18 — Target bounds and closure.** Require a sorted unique target set, valid proof digests, allowed target kinds, count within the manifest ceiling, and every target namespace permitted by A11. Every hop and transitive object used in resolution is scope-checked. v0.1 requires all targets to share one action namespace; otherwise deny.

**A19 — Derive actual effects.** Invoke the trusted effect classifier over the trusted manifest, canonical arguments, and resolved target set. Do not read `claimed_effects` for this step.

**A20 — Effect validation.** Require a sorted unique effect set; valid target indexes; allowed effect classes/units; count within ceiling; integer quantities; and each effect's target, namespace, externality, reversibility, and risk deterministically defined. Unknown or indeterminate effects deny.

**A21 — Wrapper/meta-effect closure.** If the operation invokes or delegates to another command, script, redirect, batch, API, or meta-tool, require the classified effects to cover the delegated final effects. A wrapper-only process effect is insufficient and denies.

**A22 — Effective risk.** Compute effective risk as the maximum of manifest base risk, effect risk, target class, sandbox/externality, and trusted policy escalation. Proposal/evidence risk labels are ignored.

**A23 — Effective limits.** Compute each `LimitAtom` as the minimum applicable ceiling across the manifest, grants, side-effect policy, approval, and executor hard bounds. Missing required limits or unknown limit ids deny.

**A24 — Idempotency rule.** Derive the idempotency key under the trusted operation profile. If idempotency is required and no stable key can be derived, deny. If the key is already in-flight or completed in a state that forbids repetition, deny. Proposal-supplied idempotency is not authoritative.

**A25 — Construct canonical action.** Construct `CanonicalAction/0.1` solely from trusted manifest data and trusted-derived canonical arguments/targets/effects/risk/sandbox/limits/idempotency. Compute `canonical_action_digest`. Never accept a caller-provided digest.

**A26 — Concrete grant match.** Match the canonical action against current trusted grants. Every required permission scope must be satisfied. Matching MUST constrain at least: exact tool, exact operation, action namespace, canonical target predicates, effect classes, quantities, durations/limits, externality, risk ceiling, validity window, and approval mode. Tool-only or free-form-prose matching is forbidden. All matched grants are recorded; no grant may widen another beyond its own terms.

**A27 — Side-effect policy.** Evaluate the exact current side-effect policy against the canonical action and matched grants. Policy may narrow, escalate risk/approval/sandbox, or deny; it can never be weakened by a request, proposal, manifest description, evidence, or tool output.

**A28 — Approval requirement.** Determine approval requirement as the strictest of manifest, effective risk, effects, targets, grants, and side-effect policy.

**A29 — Approval validation.** If required, load a current trusted approval record that is unrevoked, unexpired, issued by an allowed human/authority, and bound to the exact `canonical_action_digest`, task, namespace, manifest version/digest, limits, and grant snapshot. Textual approval, working-memory state, copied email, evidence, skill-card fields, or tool output never qualifies. If not required, no proposal-supplied approval reference is consulted.

**A30 — Completion-contract isolation.** Verify the active completion contract is authority-store sourced and unchanged. It does not authorize the current action; this check prevents evidence or model output from replacing/weakening later completion criteria.

**A31 — Evidence-dependency gate.** Apply the manifest operation's exact rule:

- `none`: no evidence-sufficiency claim is needed, but all packet/scope/freshness checks still stand.
- `packet_answerable`: require authentic `packet_disposition == answerable`, no provenance failure, no relevant current contradiction, and all operation-declared evidence requirements satisfied.
- `validated_claims`: require `packet_answerable` plus the exact trusted validators named by policy/manifest to return fresh bound `TrustedStatus` success.

Navigation nodes never satisfy evidence. Working memory never satisfies evidence or authority. An unresolved hierarchy frontier cannot be treated as proof of absence; an absence-dependent action additionally requires the trusted retrieval-completeness predicate specified by policy.

**A32 — Freshness recheck before issue.** Re-read current grant/revocation epoch, side-effect policy, approval, manifest registry/artifact digest, tool health, packet/corpus/working-state currentness, and relevant validator statuses. Any change since A05–A31 denies. This is the authorization-side TOCTOU barrier.

**A33 — Atomic permit reservation.** Atomically reserve a unique `(permit_id, nonce, idempotency_key, canonical_action_digest)` in the trusted permit store only if no conflicting reservation exists and all current epochs equal those checked at A32.

**A34 — Permit construction.** Construct the immutable `lifeorch.action_permit/0.1` from trusted values only. Set expiry to the minimum allowed remaining lifetime. Compute and store `permit_digest`.

**A35 — Permit non-disclosure.** Return the permit only over the privileged executor/coordinator channel. The model-facing result may receive at most a non-authoritative status such as `proposal_accepted_for_execution`; it never receives permit bytes, nonce, grant details, hidden targets, or privileged denial reasons.

**A36 — Security audit.** Append a bounded structured security event containing trusted ids/digests and reason code. Do not copy attacker-controlled evidence, arguments, snippets, paths, filenames, tool text, or model prose into the privileged log unless separately length-bounded and explicitly escaped in a non-executable data field. Ordinary caller still receives only the constant denial object.

### Authorization output

Exactly one of:

- `DENY`: constant caller-visible denial, no permit, no state diff.
- `PERMIT`: one immutable permit in trusted store and one privileged permit reference for the executor.

There is no “ask the model,” “best effort,” “probably safe,” or partial authorization state.

## 6. Enforcement-boundary obligations

### Boundary A — Storage, retrieval, derivation, and packet assembly

A1. Code-level origin wrappers or equivalent immutable metadata distinguish `Authority`, `Request`, `Untrusted`, and `TrustedStatus` at every producer/consumer boundary.

A2. `control_plane` is populated only from the authority store. Retrieval, evidence, navigation, working memory, skill/procedure records, model output, and tool text cannot write or merge into it.

A3. Ordinary copy, summary, cluster, decode, transform, derivation, deduplication, or promotion preserves non-authoritative origin. Authority-store writes and promotions use a separate elevated path not callable by a model proposal.

A4. Namespace closure uses the one canonical imported `ns_permitted` rule at every retrieval stage, graph hop, derivation/provenance edge, navigation object, working-state access, diagnostic channel, proposal target resolution, status lookup, and action effect.

A5. Cross-namespace violations abort fail-closed. Caller-visible output is constant and contains no identifying metadata. Detailed identifiers go only to the privileged local security log.

A6. `provenance_mode` is preserved. `derived_record` and `aggregate` records do not become authoritative merely because their sources were authoritative as evidence; epistemic authority is not execution authority.

A7. Navigation remains `candidate_role=navigation` and cannot be copied/cast into evidence. Working memory remains `content_role=working_state, can_instruct=false`, accessible only by exact task id AND effective namespace.

### Boundary B — Model-prompt rendering

B1. One canonical renderer emits `control_plane`, `task_input`, `working_memory`, then `evidence`, with evidence/navigation/working text escaped or length-prefixed and clearly role-labelled.

B2. Evidence text is never interpolated into control templates, manifest definitions, grant fields, approval fields, permit fields, or completion predicates.

B3. Renderer output and source hashes are auditable; delimiter and Unicode attacks cannot alter the parsed structural packet even though they may influence model semantics.

B4. Boundary B is defense in depth only. Passing prompt-injection probes is not authorization proof.

### Boundary C — Coordinator action authorization (decisive)

C1. The model emits only `lifeorch.action_proposal/0.1` over an untrusted proposal channel.

C2. One deterministic deny-by-default reference monitor performs §5. No alternate coordinator, skill, plugin, macro, or model path may issue a permit.

C3. Actual targets and effects are derived from the trusted manifest after canonicalization and resolution. `claimed_effects` is never trusted.

C4. Grants constrain concrete operation, canonical target, effects, quantities, duration/limits, namespace, risk, validity, and approval.

C5. The monitor issues a one-shot permit bound to the exact canonical action digest and current trusted snapshots.

C6. Any indeterminate state denies. Every decision and mutation test is model-independent.

### Boundary D — Executor

D1. The executor rejects raw model output, action proposals, tool-call JSON, evidence, working memory, skill cards, and caller-created permit objects.

D2. It accepts only a privileged permit reference that resolves to an `issued` permit in the trusted store.

D3. Before claim it verifies permit digest, issuer/version, expiry, nonce, store epoch, grant/approval/policy revocation, manifest/artifact digest, tool health, and canonical action digest.

D4. It re-resolves dynamic target identities and requires an exact match. Any TOCTOU substitution denies with no effect.

D5. It atomically claims the permit, applies the exact sandbox and limits, executes only the permitted operation, and meters effects.

D6. It captures a trusted structured state diff/status and stores untrusted stdout/stderr/response text separately. Tool text cannot change policy or completion.

D7. It forbids any undeclared effect and never expands effects during execution. Follow-up work requires a new proposal and permit.

D8. Permit reuse, expired/revoked permits, manifest drift, digest mismatch, and idempotency conflicts fail closed.

## 8. Model-independent P0-1 acceptance gate

### 8.1 Universal property U-AUTHORITY — authority integrity

For every test case and every bounded replacement/mutation of any `Request` or `Untrusted` value in evidence bodies, metadata, filenames, record ids, diagnostics, navigation, expand hints, working memory, skill/procedure cards, model output, proposal fields, claimed effects, or tool text:

1. `AuthorityConfigDigest = H(control_plane authority snapshot, grant snapshot, side-effect policy, trusted manifest, approval state, completion contract, validator registry)` is byte-identical unless an explicit elevated authority operation occurred outside the test.
2. No mutated value becomes or modifies an authority object.
3. Any issued permit's manifest, grants, policy, approval, completion-contract reference, and issuer all resolve to trusted stores.
4. For a fixed parsed proposal and fixed trusted snapshots, changing only `claimed_effects`, evidence/metadata text, fake manifest fields, fake approvals, fake completion text, or fake health text cannot change the decision or the permit's canonical action digest. If an evidence change causes the model to emit a different proposal, that new proposal is evaluated independently under the same unchanged authority rules.
5. Every authority violation yields constant denial, no permit, and no state diff.

**Machine assertion:**

```text
forall untrusted_mutation m:
  authority_digest(run(m)) == authority_digest(run(baseline))
  and issued_permit(run(m)) implies trusted_origin_closure(permit)
```

The proposal itself may change and a different requested action may be denied or separately authorized; the authority rules cannot change.

### 8.2 Universal property U-SCOPE — scope integrity

For every packet, proposal, resolver step, graph hop, target, effect, status, diagnostic, and completion subject:

1. `effective_allowed_namespaces` equals the existing request/grant intersection; it is never a union and never proposal-derived.
2. Every visible or authorization-relevant object satisfies the imported `ns_permitted` predicate.
3. Every permitted target/effect belongs to the permit's single `effective_namespace` in v0.1.
4. Alias/path/recipient/redirect resolution cannot cross scope.
5. A scope violation returns exactly the constant ordinary denial bytes, no identifying metadata, no permit, and no state diff.

**Machine assertion:**

```text
permit implies
  all(ns_permitted(x.namespace, {permit.effective_namespace})
      for x in targets + effects + trusted_status_subjects)

scope_violation implies
  caller_bytes == CONSTANT_DENIAL
  and permit_count_delta == 0
  and state_diff == EMPTY
```

### 8.3 Universal property U-ROLE — role integrity

1. Only `Authority` values define control-plane policy, grants, manifests, approval requirements/state, permits, and completion predicates.
2. `Request` can narrow through intersection but never grant.
3. Navigation never becomes evidence; working memory never becomes evidence, authority, approval, or trusted status.
4. Derived/aggregate records preserve non-authoritative origin through every hop.
5. Raw model output/action proposals never reach the executor.
6. Completion uses only allowlisted bound `TrustedStatus`; untrusted tool/evidence/model text cannot satisfy it.

**Machine assertion:**

```text
no_path(Untrusted | Request, Authority_constructor)
no_path(action_proposal, executor_effect_entry)
completion_true implies all(leaf.actual.origin == TrustedStatus
                            and leaf.source in authority_allowlist)
```

The only exception is an explicit elevated promotion path, which is out of scope for ordinary P0-1 actions and must have separate human authorization tests.

### 8.4 Universal property U-EFFECT — effect integrity

1. Every nonempty state diff is associated with exactly one consumed permit.
2. Every permit is associated with exactly one canonical action digest derived from the trusted current manifest, canonical args, resolved targets, derived effects, namespace, risk, sandbox, limits, and idempotency key.
3. Actual executor effects are a subset of the permit's authorized effects and within all limits.
4. Denial, malformed proposal, raw model output, invalid/reused/revoked/expired/substituted permit, stale grant, stale approval, manifest drift, target drift, or digest mismatch produces no effect.
5. A permit can transition to an effect-starting state at most once.
6. Completion true does not authorize an effect, and an effect/result text does not imply completion.

**Machine assertion:**

```text
state_diff != EMPTY implies
  exists_exactly_one p:
    p.state == consumed
    and recompute_digest(execution_input) == p.canonical_action_digest
    and actual_effects <= p.authorized_effect_set
    and within_limits(actual_usage, p.limits)

not valid_one_shot_permit implies state_diff == EMPTY
```

### 8.5 Mandatory fixture families

The gate includes at least these ten committed families, each with canonical fixture hashes and named property expectations rather than whole-packet byte snapshots:

1. Direct evidence/fake-control/fake-completion injection, including payload split across chunks.
2. Delimiter breakout, Unicode/bidi/zero-width/homoglyph, base64/hex/double-encoding, and NUL-bearing identifiers.
3. Navigation/synopsis/expand-hint/prune-reason/generated-query injection.
4. Working-memory poisoning, stale-head use, and “approval received” authority laundering.
5. Skill/procedure cards claiming permission, health, risk, manifest fields, effects, or no approval.
6. Cross-namespace leakage through ids, paths, graph hops, aggregates, exact lookup, diagnostics, and denial side channels.
7. Stale/superseded/currentness attacks and withheld successors.
8. Multi-hop delayed injection through generated queries, descendants, summaries, and later working state.
9. Parser/canonicalization/replay/TOCTOU attacks: duplicate keys, downgrade, coercion, wrappers, redirects, symlinks/junctions, wildcard/env expansion, argument substitution, grant revocation, manifest drift, permit reuse.
10. Fully malicious mock-model proposals against mock authorizer/executor, including raw tool-call and permit-shaped output.

### 8.6 Mandatory seeded security mutations

Every mutation below MUST be killed by at least one deterministic test. “Killed” means a test that passes on the reference implementation fails on the mutated implementation for the named security property.

#### Authority mutations

- **M-A01:** Allow an evidence object with key `permission_grants` to merge into `control_plane`.
- **M-A02:** Accept a skill/procedure card's `required_permission_scopes`, risk, approval, health, or effect fields as manifest data.
- **M-A03:** Treat working-memory text “approval received” as an approval record.
- **M-A04:** Treat tool stdout/stderr or response JSON as trusted approval or completion status.
- **M-A05:** Let the proposal select `grant_snapshot_ref`, `issuer`, `side_effect_policy_ref`, or `completion_contract_id`.
- **M-A06:** Strip origin labels during summary/aggregate/cluster/derivation and allow the result into authority.
- **M-A07:** Permit ordinary model-initiated promotion into the authority store.
- **M-A08:** Use `claimed_effects` for grant matching or permit construction.
- **M-A09:** Accept caller/model-supplied `model_provenance` instead of adapter-attached provenance.
- **M-A10:** Let evidence/model text alter tool health or operation enabled state.

#### Scope mutations

- **M-S01:** Use raw `task_input.namespace` without intersecting grants.
- **M-S02:** Implement intersection as union.
- **M-S03:** Add implicit wildcard, prefix, parent, shared, or empty-means-all semantics.
- **M-S04:** Omit `ns_permitted` on one graph/retrieval/resolver hop.
- **M-S05:** Scope-check only the target envelope, not transitive provenance/derivation/aggregate members.
- **M-S06:** Allow a symlink, junction, reparse point, redirect, alias, or recipient map to resolve outside scope.
- **M-S07:** Allow a multi-namespace target/effect set in a v0.1 permit.
- **M-S08:** Return forbidden ids, paths, snippets, counts, namespace names, differing error codes, detailed reasons, or a caller-visible deterministic branch/step-count signal that reveals where scope failed.
- **M-S09:** Log attacker-controlled identifying payload into an ordinary/nonprivileged log.
- **M-S10:** Allow completion status from an out-of-scope object/source.

#### Role mutations

- **M-R01:** Cast `candidate_role=navigation` into evidence or let it satisfy evidence coverage.
- **M-R02:** Cast working memory into evidence, authority, approval, or trusted status.
- **M-R03:** Let a derived/aggregate record become execution authority because its source has high epistemic authority.
- **M-R04:** Route raw model tool-call JSON directly to the executor.
- **M-R05:** Let the executor accept `lifeorch.action_proposal/0.1` as an invocation.
- **M-R06:** Let the executor accept permit-shaped caller JSON without trusted-store resolution.
- **M-R07:** Let model/evidence prose “task complete” satisfy completion.
- **M-R08:** Let untrusted tool text be parsed as a completion leaf actual.
- **M-R09:** Render permit bytes/nonce/grant details back into ordinary model context.
- **M-R10:** Let an absence inferred from an unresolved/pruned hierarchy frontier satisfy an absence-dependent validator.

#### Effect, canonicalization, replay, and TOCTOU mutations

- **M-E01:** Skip strict duplicate-key rejection.
- **M-E02:** Permit schema downgrade or unknown argument fields.
- **M-E03:** Coerce string/float/bool/array types.
- **M-E04:** Skip argument canonicalization.
- **M-E05:** Resolve targets using caller spelling rather than canonical identity.
- **M-E06:** Fail to resolve aliases, redirects, wildcards, environment expansion, symlinks, junctions, or wrappers.
- **M-E07:** Classify only the wrapper/meta-tool effect, not delegated effects.
- **M-E08:** Match grants only on tool id, omitting operation.
- **M-E09:** Omit canonical targets from grant matching.
- **M-E10:** Omit effect class/quantity/duration/externality/risk from grant matching.
- **M-E11:** Let policy reduce manifest/grant risk or approval requirements.
- **M-E12:** Skip required approval.
- **M-E13:** Accept approval bound to a different digest, task, namespace, grant snapshot, manifest version, or limits.
- **M-E14:** Omit arguments from `canonical_action_digest`.
- **M-E15:** Omit resolved targets from the digest.
- **M-E16:** Omit derived effects from the digest.
- **M-E17:** Omit namespace, risk, sandbox, limits, manifest digest, or idempotency key from the digest.
- **M-E18:** Trust a caller-supplied action digest.
- **M-E19:** Issue a permit when packet `non_execution=true`.
- **M-E20:** Accept a stale/revoked grant snapshot.
- **M-E21:** Accept a stale/revoked approval.
- **M-E22:** Ignore packet/corpus/tree/working-state drift required by policy.
- **M-E23:** Ignore manifest or installed-artifact drift.
- **M-E24:** Ignore stale/unhealthy tool status.
- **M-E25:** Remove the A32 final freshness recheck.
- **M-E26:** Issue two permits from one atomic reservation.
- **M-E27:** Allow permit reuse after claim/consume/reject.
- **M-E28:** Ignore permit expiry, nonce, store epoch, or revocation.
- **M-E29:** Re-resolve a different target at execution and continue.
- **M-E30:** Permit effects not present in `authorized_effect_set` or over a limit.
- **M-E31:** Produce a state diff after authorization denial or executor preflight rejection.
- **M-E32:** Treat a crash after `effect_started=true` as making the permit reusable.
- **M-E33:** Retry a failed operation under the same permit.
- **M-E34:** Execute rollback/follow-up under the original permit when not included in the canonical action.
- **M-E35:** Treat missing/stale/malformed completion status as success.
- **M-E36:** Let status from another task/action/permit/object/validator version satisfy completion.

### 8.7 Gate result

The deterministic P0-1 gate passes only when all are true:

1. All mandatory fixtures pass on two consecutive runs with identical property results and canonical hashes. Positive permit-path tests use an explicitly marked test-only mock authority packet with `non_execution=false`; the real shipped #40 packet path must continue to prove deterministic denial while its authentic packets carry `non_execution=true`.
2. The fixed-seed mutational fuzzer preserves U-AUTHORITY, U-SCOPE, U-ROLE, and U-EFFECT.
3. Every seeded mutation M-A01 through M-E36 is killed.
4. Every denied proposal yields no permit and no state diff.
5. No raw-model-output path reaches the executor.
6. Every state diff has exactly one consumed, digest-matching, nonreused permit.
7. Cross-namespace failures return constant caller bytes with no identifying data.
8. One canonical or byte-equivalent implementation exists for strict parsing/serialization, `ns_permitted`, target/effect canonicalization interfaces, grant matching, and permit verification.
9. The same producer-to-consumer tests pass on real #36/#37/#40 packet outputs, not only synthetic objects.
10. Actual-model probes, if run, are reported only as regression measurements and cannot compensate for a failed deterministic property.

## 9. Gaps and freeze blockers

The four schemas above can be committed as the action-layer target, but a **clean operational freeze** is blocked until the following are resolved. Ranked by blocking severity:

### Blocker 1 — Exact permission-grant and side-effect-policy schemas

`control_plane.permission_grants[]` and `side_effect_policy` exist, but the supplied digest does not freeze their item-level matching language, versioning, revocation, target predicates, quantitative limits, validity windows, risk ceilings, approval modes, or conjunction semantics. A tool-only grant is explicitly inadequate. The freeze must either:

- define `lifeorch.permission_grant/0.1` and `lifeorch.side_effect_policy/0.1`, or
- freeze an exact byte-equivalent `GrantView`/`PolicyView` interface consumed by A26/A27.

Without this, grant matching is implementation-defined and the P0-1 gate is not decidable.

### Blocker 2 — Approval-record contract and digest binding

The digest requires explicit approval when policy/risk demands it but does not define approval issuer identity, version, expiry, revocation, action-digest binding, scope, limits, or reuse. A trusted `lifeorch.action_approval/0.1` contract is required before any approval-gated action.

### Blocker 3 — Permit-store authenticity and atomic state machine implementation

The schema specifies store-backed permits and one-shot transitions, but the trusted-process/IPC boundary, ACLs, crash recovery, atomic compare-and-swap mechanism, permit-store epoch, and privileged executor channel must be selected and tested on Windows. A serialized JSON object alone is not sufficient authenticity.

### Blocker 4 — Per-tool canonical target and effect profiles

The generic resolver/effect interfaces are frozen here, but each action-capable tool needs ratified profiles for Windows path/reparse-point/device/ADS behavior, aliases, recipients, redirects, wrappers, future-create targets, target proof digests, effect vocabulary, and limit units. Until a tool has those profiles and mutation fixtures, its operations remain disabled/proposal-only.

### Blocker 5 — Trusted structured executor/status contracts and validator registry

Completion cannot depend on tool prose. The exact executor status schema, state-diff schema, object/artifact identity rules, validator registry, validator code-digest checks, and status supersession/revocation rules must be frozen. The completion contract above defines what it may consume, not every tool-specific status payload.

### Blocker 6 — Freshness policy for packet/corpus/tree/working state

The digest says stale packet/grant/corpus/manifest/approval replay must fail, but “stale packet” is not fully operationally defined for actions. Ratify whether every action requires the latest corpus/tree/working-state head or whether a still-available pinned snapshot may remain valid for a bounded interval. The safest v0.1 default is latest-current-only; any relaxation must be explicit per policy and covered by replay tests.

### Blocker 7 — Activation transition for `non_execution`

The current packet contract mandates `non_execution:true`. After the suite passes, an explicit decision must define who may produce `false`, which packet/compiler/version does so, how rollback to read-only occurs, and which tool manifests are enabled. No field redesign is needed, but activation cannot be implicit.

### Blocker 8 — Canonical parser/library ownership and cross-module equivalence

An owner must be named for strict JSON parsing, canonical serialization, action digest construction, grant matching, and permit verification. If separate implementations exist, the fold must prove byte-identical results over shared fixtures. Parser/canonicalization differentials are a top-ranked risk.

### Blocker 9 — Constant-failure and privileged-security-log contract

The ordinary failure bytes are specified here, but the API surfaces that must use them, bounded logging fields, ACL, retention, redaction, and response-size/observable-step equalization policy need implementation ownership. The log must not become another attacker-controlled execution or exfiltration channel.

### Blocker 10 — Idempotency, transaction, rollback, and crash semantics per operation

The generic state machine is defined, but each operation must declare stable idempotency identity, effect-start boundary, state-diff capture, retry prohibition/strategy, compensating action, and crash recovery. “Reversible” without an executable verified rollback profile is not sufficient.

### Blocker 11 — Tool-health semantics

Each tool needs an actual trusted health probe, freshness period, failure codes, and registry ownership. Self-reported health from a card, tool response, or model is forbidden.

### Blocker 12 — Elevated promotion/authority-store write path

The substrate requires origin labels to survive ordinary derivation. A separate human/administrator promotion and authority-store mutation contract is required before any system can convert derived information into policy, grants, manifests, completion predicates, or trusted validators. P0-1 must prove the ordinary model path cannot call it.

### Blocker 13 — Clarification of “evidence cannot change skill selection”

The older packet prose is overbroad if read as requiring the model's selected proposal to be invariant under evidence changes. The deterministic freeze should state that evidence cannot expand eligibility or alter permissions/risk/health/effects/approval/manifest/completion, and every selected operation is independently authorized. If literal evidence-immune selection is desired, operation selection itself must be deterministic code and separately specified.

### Blocker 14 — Real-module integration fixture and ownership

The shared fixture corpus, fixed fuzzer seed, mutation framework, mock coordinator/executor, real #36/#37/#40 chain, and test-report schema need named module owners. The gate cannot be declared passed using only isolated schema tests.
